## Alcance de producto establecido

U0.2 establece dos superficies explícitas del producto.

### Superficie pública

- `/` landing pública;
- `/apps` catálogo de aplicaciones;
- `/apps/:slug` presentación de aplicación;
- `/demo/:slug/*` demo de propuesta pública, compartible y navegable;
- `/docs/*` entrada de documentación pública;
- `/components` entrada pública de la librería de componentes;
- `/login` acceso al Compositor de aplicaciones.

### Superficie autenticada

- `/composer/*` espacio de trabajo protegido del Compositor.

Las demos públicas no exponen deliberadamente la exportación ZIP. La exportación pertenece al flujo autenticado del Compositor.

## Caso de uso para propuestas comerciales

Una demo frontend es un artefacto comercial de primera clase. Puede ensamblarse para la aplicación solicitada por un cliente potencial, publicarse bajo una URL directa estable, compartirse en una propuesta de una plataforma freelance y posteriormente promoverse al catálogo público de aplicaciones cuando resulte útil.

La demo es técnicamente honesta: durante la fase Blueprint/demo sus datos pueden ser simulados y el comportamiento de backend/API puede no existir todavía.

## Destino canónico de publicación

WebBlueprint está destinado a publicarse mediante **EliasWorks**, con el dominio canónico:

- `https://eliasworks.uy`

Render **no** es un destino de producción ni un despliegue canónico de WebBlueprint.

Durante U0.2 se creó un sitio estático temporal en Render únicamente para obtener evidencia visual visible en navegador cuando la navegación local estaba bloqueada. Ese servicio no forma parte de la arquitectura del producto, no define el roadmap de despliegue y no debe usarse como base para decisiones de hosting de producción.

## Auditoría de hosting de EliasWorks

U0.2 verificó el entorno existente de publicación de EliasWorks en lugar de inferirlo desde el preview temporal.

Arquitectura observada:

```text
LuisHdezE/erp_eliasworks
        ↓
GitHub Actions sobre main
        ↓
Build PHP 8.3 + Node
        ↓
FTP
        ↓
public_html/
        ↓
eliasworks.uy
```

La raíz de EliasWorks ya está ocupada por la aplicación de portafolio y WebBlueprint no debe sobrescribirla.

La cuenta de hosting también dispone de un patrón probado para frontend estático: eFactura compila su WebApp Vite y publica el bundle generado dentro de un directorio dedicado bajo `public_html/`.

El fallback SPA de Apache ya se utiliza correctamente en ese stack de hosting mediante `.htaccess`.

### Preparación de U0.2 para deep links

WebBlueprint se prepara para una ruta o subdominio bajo EliasWorks sin elegir prematuramente uno de los dos:

- `BrowserRouter` utiliza `BASE_URL` de Vite como basename;
- un build en raíz/subdominio puede mantener la base `/`;
- un despliegue bajo ruta puede proporcionar una base de build como `/webblueprint/`;
- `public/.htaccess` reescribe solicitudes desconocidas que no corresponden a archivos/directorios hacia `index.html`;
- rutas como `demo/pet-shop/dashboard` disponen así del mecanismo de fallback SPA necesario para el host final.

La ruta/subdominio exacta y el cableado de CD permanecen gobernados por **U0.6 · CD inicial / publicación EliasWorks**. La aceptación real de recarga/runtime desplegada en EliasWorks también pertenece a U0.6 porque U0.2 no introduce un despliegue de producción.

## Implementación como fuente de verdad

El registro de aplicaciones es la fuente de verdad actual para la metadata pública de aplicaciones y la estructura de demos.

La misma definición de aplicación gobierna:

- metadata del catálogo/presentación pública;
- capacidades;
- páginas de demo pública;
- navegación de la demo pública;
- variante de shell permitida.

`Pet Shop` declara actualmente `vertical-light-menu`.

## Variantes de shell gobernadas

El código expone exactamente estas variantes permitidas:

- `collapsible-menu`;
- `vertical-dark-menu`;
- `vertical-light-menu`.

Todas son layouts con menú lateral izquierdo. Los layouts con menú horizontal quedan fuera del alcance de WebBlueprint.

Los valores permitidos están centralizados en `src/shell/shell.types.ts` y validados por tests del registro.

## Arquitectura de shell reutilizable

`LeftAppShell` controla las mecánicas reutilizables para:

- sidebar izquierda fija en escritorio;
- drawer móvil responsive;
- estado de navegación activa;
- modo contraíble en escritorio cuando la variante seleccionada es `collapsible-menu`;
- tratamiento claro/oscuro de la sidebar;
- topbar sticky;
- slots reutilizables para pie y acciones.

Tanto el Compositor autenticado como las demos públicas consumen este shell en lugar de implementar sistemas separados de sidebar.

`WorkspaceShell` es una composición específica del Compositor construida sobre `LeftAppShell`.

En esta etapa, los visuales representativos de aplicaciones se generan con primitivas UI de WebBlueprint en lugar de capturas externas de templates.

## Refinamiento Visual V2

El feedback explícito de U0.2 refinó la implementación Style 1 hacia:

- uso más eficiente del espacio visible;
- menor padding en secciones/cards;
- tamaños de H1 y títulos de sección más contenidos;
- dimensiones compactas de shell orientadas a productividad;
- azul fresco como color primario/de acción predeterminado;
- slate reservado para jerarquía de texto en lugar de dominar los CTA;
- `vertical-dark-menu` conservado únicamente como variante de shell opcional soportada.

Estas reglas quedaron registradas en el baseline gobernado Style 1 en lugar de vivir solo en estilos a nivel de página.

## Frontera de autenticación

La autenticación permanece deliberadamente reemplazable.

Flujo actual:

```text
Ruta protegida
    ↓
Contexto / hook de sesión
    ↓
Proveedor de sesión
    ↓
Comportamiento de sesión simulado
```

Las páginas no realizan comprobaciones de autenticación ad hoc.

Se requerirá un backend/servicio confiable futuro si la autorización de nivel producción debe impedir la generación/descarga ZIP a usuarios no autorizados.
