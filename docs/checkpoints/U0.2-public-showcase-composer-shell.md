## Product scope established

U0.2 establishes two explicit product surfaces.

### Public surface

- `/` public landing;
- `/apps` application catalog;
- `/apps/:slug` application presentation;
- `/demo/:slug/*` public/shareable navigable proposal demo;
- `/docs/*` public documentation entry;
- `/components` public component-library entry;
- `/login` App Composer access.

### Authenticated surface

- `/composer/*` protected App Composer workspace.

Public demos intentionally do not expose ZIP export. Export belongs to the authenticated Composer flow.

## Commercial proposal use case

A frontend demo is a first-class commercial artifact. It can be assembled for a prospective client's requested application, published under a stable direct URL, shared in a freelance-platform proposal, and later promoted into the public application catalog when useful.

The demo is technically honest: during the Blueprint/demo phase its data may be mock and backend/API behavior may not yet exist.

## Canonical publication target

WebBlueprint is intended to be published through **EliasWorks**, with the canonical domain:

- `https://eliasworks.uy`

Render is **not** a WebBlueprint production or canonical deployment target.

A temporary Render static-site preview was created during U0.2 only to obtain browser-visible visual evidence when local browser navigation was blocked. That service is not part of the product architecture, does not define the deployment roadmap, and must not be used as the basis for production hosting decisions.

The exact EliasWorks path/subdomain and deployment mechanism will be governed when the site is wired for continuous delivery.

Deep proposal URLs such as `/demo/pet-shop/dashboard` must support direct navigation and refresh on the final EliasWorks publication surface. How that rewrite/fallback is implemented depends on the actual EliasWorks hosting stack and must be validated there rather than against Render-specific behavior.

## Source-of-truth implementation

The application registry is the current source of truth for public application metadata and demo structure.

The same application definition now drives:

- public catalog/presentation metadata;
- capabilities;
- public demo pages;
- public demo navigation;
- permitted shell variant.

`Pet Shop` currently declares `vertical-light-menu`.

## Governed shell variants

Code now exposes exactly these allowed variants:

- `collapsible-menu`;
- `vertical-dark-menu`;
- `vertical-light-menu`.

All are left-side menu layouts. Horizontal menu layouts are outside WebBlueprint scope.

The allowed values are centralized in `src/shell/shell.types.ts` and validated by registry tests.

## Reusable shell architecture

`LeftAppShell` owns the reusable mechanics for:

- fixed left sidebar on desktop;
- responsive mobile drawer;
- active navigation state;
- collapsible desktop mode when the selected variant is `collapsible-menu`;
- light/dark sidebar treatment;
- sticky topbar;
- reusable footer/action slots.

Both the authenticated Composer and public application demos consume this shell rather than implementing separate sidebar systems.

`WorkspaceShell` is a Composer-specific composition over `LeftAppShell`.

## Public Style 1 foundation

Implemented:

- shared `PublicShell` with public navigation and footer;

- Style 1 landing hero;
- reusable `ApplicationPreview`;
- reusable `ApplicationCard`;
- application catalog using shared cards;
- application presentation using shared preview;

- Composer workspace using the approved left-side shell pattern.

Representative application visuals are generated from WebBlueprint UI primitives rather than external template screenshots at this stage.

## Visual V2 refinement

Explicit U0.2 feedback refined the Style 1 implementation toward:

- more efficient use of viewport space;
- smaller section/card padding;
- more contained H1 and section-heading sizes;
- compact productivity-oriented shell dimensions;
- fresh blue as the default primary/action color;
- slate reserved for text hierarchy rather than dominant CTA treatment;
- `vertical-dark-menu` retained only as an optional supported shell variant.

These rules are now recorded in the governed Style 1 baseline rather than living only in page-level styling.

## Authentication boundary

Authentication remains intentionally replaceable.

Current flow:

```text
Protected route
    ↓
Session context / hook
    ↓
Session provider
    ↓
Mock session behavior
```

Pages do not perform ad-hoc authentication checks.

A future trusted backend/service is still required if production-grade authorization must prevent unauthorized ZIP generation/download.
